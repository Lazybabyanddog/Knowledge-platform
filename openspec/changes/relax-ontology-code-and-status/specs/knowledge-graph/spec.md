# Spec Delta

## MODIFIED Requirements

### Requirement: 本体管理

系统 SHALL 允许管理员定义实体类（如"人员""制度""系统"）与关系类型（如"属于""负责""依赖"），并为每个定义维护编码、名称、描述，以编码作为稳定标识。

系统 SHALL 允许实体类之间存在继承关系，且禁止形成环。

系统 SHALL 允许为关系类型指定起点类与终点类，抽取时据此校验合法性。

系统 SHALL 要求编码以字母开头、仅由字母、数字与下划线组成、长度 2–64，大小写均可，并按原样存储与比较。

系统 SHALL 为每个实体类与关系类型维护状态：`0` 表示有效、`1` 表示失效。创建时状态必传；更新时可选，但一旦提供只接受 `0` 或 `1`；缺失或越界返回 400。

#### Scenario: 创建实体类

- **WHEN** 管理员创建编码为 `policy`、名称为"制度"、状态为 `0` 的实体类
- **THEN** 系统保存该类，后续抽取可引用它

#### Scenario: 编码重复

- **WHEN** 管理员创建已存在的编码 `policy`
- **THEN** 系统返回 409，提示编码已存在

#### Scenario: 继承成环

- **WHEN** 管理员将类 A 的父类设为 A 的子孙类
- **THEN** 系统返回 400，提示会形成环

#### Scenario: 关系类型约束

- **WHEN** 关系类型"负责"的起点类为"人员"、终点类为"系统"
- **THEN** 抽取产生的、起点不是人员或终点不是系统的关系被标记为不合规

#### Scenario: 大小写混合的编码

- **WHEN** 管理员创建编码为 `HAS_PLAINTIFF` 的关系类型，起点类为"人员"、终点类为"案件"，状态为 `0`
- **THEN** 系统创建成功，并在列表与详情中原样返回编码 `HAS_PLAINTIFF`
- **THEN** 该编码与 `has_plaintiff` 视为两个不同的编码，可同时存在

#### Scenario: 编码形态非法

- **WHEN** 管理员提交以数字或下划线开头、包含连字符或空格的编码（如 `2party`、`has-plaintiff`）
- **THEN** 系统返回 400，并提示编码需以字母开头、仅含字母数字与下划线

#### Scenario: 创建缺少状态

- **WHEN** 管理员创建实体类或关系类型时未提供 `status`
- **THEN** 系统返回 400，提示参数校验失败且指出缺失字段为 `status`
- **THEN** 该定义不被保存

#### Scenario: 状态取值越界

- **WHEN** 管理员创建或修改实体类、关系类型时把 `status` 设为 `2`、`-1` 或字符串 `"active"`
- **THEN** 系统返回 400，提示状态只能是 0 或 1

#### Scenario: 失效定义默认不可见

- **WHEN** 管理员把某个实体类或关系类型的 `status` 改为 `1`
- **THEN** 默认列表不再返回该定义，抽取也不再引用它
- **THEN** 显式请求包含失效项时，列表返回该定义且 `status` 为 `1`

#### Scenario: 存量定义迁移为有效

- **WHEN** 升级到本版本并执行数据库迁移
- **THEN** 所有既有实体类与关系类型的 `status` 均为 `0`
- **THEN** 此前标记为停用的定义也变为有效，默认列表重新可见
