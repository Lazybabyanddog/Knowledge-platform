# Spec Delta

## Purpose

把低置信问答变成可研判、可处置、可追溯的治理对象，让知识缺口与答案质量问题分别被发现、分派与关闭，而不是停留在零散的用户抱怨里。

## ADDED Requirements

### Requirement: 双维度低置信判定

系统 SHALL 在问答记录形成后，分别给出检索置信与答案质量两个维度的判定结果，不得把两者合成单一置信分数。

- 检索侧硬信号 MUST 包含：未命中任何片段。
- 检索侧软信号 MUST 包含：命中数低于配置下限、最高分低于配置的标记线、最高分与末位分差小于配置值；软信号只打标，不单独使记录成为低置信记录。
- 答案质量硬信号 MUST 包含：答案中不含任何与来源编号对应的标注、使用者标记为不认可。
- 判定 MUST 输出触发原因集合，供治理端筛选与统计；记录 MUST 保留判定时的原始信号快照。
- 判定所用的标记线与阈值 MUST 可配置，且调整阈值后能对既有记录重新判定，不依赖重新采集。

#### Scenario: 无命中直接成为低置信

- **WHEN** 一次问答的检索结果为空
- **THEN** 该记录带"未命中"原因，成为待处置记录

#### Scenario: 分数偏低只是打标

- **WHEN** 一次问答命中 2 个片段，最高分低于标记线，但使用者既未评价也未中断
- **THEN** 该记录带有分数偏低的标记，但不进入待处置队列

#### Scenario: 答案没有引用

- **WHEN** 问答命中 3 个片段，但生成的答案中不含任何来源编号
- **THEN** 该记录带"答案无引用"原因，成为待处置记录

#### Scenario: 阈值调整后重新判定

- **WHEN** 管理员下调最高分标记线并触发重新判定
- **THEN** 既有记录按新标记线重新打标，无需重新提问

### Requirement: 待处置记录的形成

系统 SHALL 把满足条件的问答记录转为待处置记录，并保证并非所有记录都进入队列。

- 带任一硬信号的记录 MUST 转为待处置记录，初始状态为待研判。
- 中断与失败的记录 MUST NOT 转为待处置记录。
- 记录 MUST 只在其所属空间内被治理，不得跨空间合并或流转。
- 记录转为待处置记录 MUST NOT 修改问答记录本身的内容。

#### Scenario: 不认可触发待处置

- **WHEN** 使用者对一次正常问答标记不认可
- **THEN** 该记录转为待处置记录，状态为待研判

#### Scenario: 中断记录不进队列

- **WHEN** 使用者中途停止了生成
- **THEN** 该记录不会被转为待处置记录

### Requirement: 问题簇聚合

系统 SHALL 把指向同一问题的待处置记录聚合为一个问题簇，治理端操作的对象是簇而不是单条记录。

- 聚合 MUST 只在同一空间、同一密级的记录之间进行。
- 问题表述近似（问题向量相似度达到配置阈值），或来源文档与触发原因均相同的记录，MUST 归入同一簇。
- 每条待处置记录 MUST 只属于一个簇；簇的记录数 MUST 随新成员增加而更新。
- 簇 MUST 维护一个代表性问法与最近发生时间，用于列表展示与排序。
- 已关闭的簇 MUST NOT 接收新记录；同类问题的新记录 MUST 形成新的簇，保留原簇的处置结论不被稀释。

#### Scenario: 同一问题被多次提问

- **WHEN** 三名使用者先后提出表述不同但语义相同的问题，且都未命中
- **THEN** 三条记录归入同一簇，簇的记录数为 3

#### Scenario: 不同密级不混簇

- **WHEN** 两条语义相同的记录，一条来源为 `internal`，另一条为 `secret`
- **THEN** 两条记录分别形成各自的簇，不合并

#### Scenario: 已关闭的簇不再收新记录

- **WHEN** 一个已关闭的簇又出现了同类提问并被判为低置信
- **THEN** 系统形成新簇，原簇的状态与结论保持不变

### Requirement: 分诊处置与轨迹

具备问答治理能力的使用者 SHALL 在簇上完成分诊，处置过程可追溯。

- 可执行动作 MUST 包含：指派处理人、设置处置结论、填写备注、关闭、重开。
- 处置结论 MUST 限于：误报、知识缺口、检索失败、答案错误。
- 关闭 MUST 必须给出处置结论；未给结论的关闭 MUST 被拒绝。
- 每个动作 MUST 追加一条不可修改的轨迹，含动作类型、操作人、时间与可选备注；轨迹 MUST NOT 被覆盖或删除。
- 重开 MUST 把簇退回待研判，并保留此前的全部轨迹与结论。
- 指派与处置动作 MUST 记入审计。

#### Scenario: 关闭必须给出结论

- **WHEN** 治理者对一个簇直接执行关闭而未选择结论
- **THEN** 请求被拒绝，簇保持待研判

#### Scenario: 轨迹只增不改

- **WHEN** 治理者先标记为知识缺口并关闭，随后重开并改判为检索失败
- **THEN** 簇上有四条以上轨迹，包含两次结论变化与重开动作，此前记录仍可读

#### Scenario: 指派后可见处理人

- **WHEN** 治理者把簇指派给某位同事
- **THEN** 该簇详情显示当前处理人，并在列表可按处理人筛选

### Requirement: 治理可见性与权限

系统 SHALL 只让具备问答治理能力的使用者访问治理端，并按空间与密级限制可见范围。

- 治理端接口 MUST 要求 `qa:manage` 能力或管理员角色；普通使用者 MUST 只能访问自己的问答评价接口。
- 列表、详情与计数 MUST 按调用者的空间过滤，跨空间数据 MUST 不可见。
- 记录与簇的密级 MUST 按调用者可见密级过滤；超出可见范围的记录 MUST NOT 出现在列表、详情、簇成员与计数中。
- 不可见集合的内部结构 MUST NOT 通过错误信息泄露：对不可见簇的访问 MUST 返回未找到。

#### Scenario: 非治理者被拒绝

- **WHEN** 只有文档查看权限的使用者请求治理列表
- **THEN** 请求被拒绝

#### Scenario: 密级过滤生效

- **WHEN** 治理者的可见密级上限为 `internal`，而某个簇的成员记录均为 `secret`
- **THEN** 该簇不出现在其列表中，也无法通过标识访问

### Requirement: 队列查询与排序

系统 SHALL 提供可按治理需要检索与排序的队列视图。

- 列表 MUST 支持按状态、处置结论、触发原因、时间范围、处理人与关联文档筛选。
- 默认排序 MUST 优先考虑影响面与紧急度：含使用者不认可的簇优先，其次按记录数降序，再次按最近发生时间降序。
- 列表项 MUST 展示：代表性问法、记录数、命中片段数、触发原因、密级、最近发生时间与当前状态。
- 簇详情 MUST 能列出成员记录的提问时间与生成答案摘要，并支持跳转到触发记录的来源文档详情。

#### Scenario: 影响面优先

- **WHEN** 队列中同时存在一个被 8 人问过且无人评价的簇，和一个只被 1 人问过但被标记不认可的簇
- **THEN** 后者排在前面

#### Scenario: 从簇跳到文档

- **WHEN** 治理者打开一个由"答案无引用"触发的簇
- **THEN** 详情中列出参与生成该答案的来源文档，可跳转到文档详情查看原文
