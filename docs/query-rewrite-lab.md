# 查询改写实验室：使用与调参

改写实验室是一个**只读**实验台：同一条问题，换配置再跑一次，就能看出"查询改写到底有没有把召回变好"。
它不写文档、不建索引、不改审批数据，也不参与 `/retrieval/search` 与 `/retrieval/ask` 的线上链路。

入口：登录后左侧菜单 **知识资产 → 改写实验室**（`/rewrite-lab`，需要 `document:read`）。

## 一、一次运行发生了什么

1. **查询理解**：规则先抽特征（指代、复合连词、口语、别名、概念意图、是否有历史），模型再补意图/复杂度/候选策略。模型不可用时自动回退到纯规则，并标记降级。
2. **策略路由**：执行集 = 规则命中 ∩ Allowlist，按优先级 `上下文 → 实体 → 语义 → 拆解 → Multi` 截断到预算。模型给的候选策略**只作证据，不触发执行**。
3. **先跑对照组**：原始查询先检索一次并保留结果；后面任何一步超时或预算耗尽，都还有真实结果可返回。
4. **串行执行策略**：文本类策略（上下文/实体/语义）改写主查询并依次串联；扩展类（拆解/Multi）只产出额外检索查询，不改主查询。
5. **双路检索**：对照组与改写组走**同一套过滤条件**（`_base_stmt`），只有查询文本不同，否则 `lift` 没有可比性。
6. **评估**：`top1 >= threshold` 且 `above_tau >= min_evidence` 才算"召回充分"；不充分时允许一次二阶段补充（仍受 Allowlist 与预算约束）。
7. **融合**：按 `chunk_id` 去重、记录来源、RRF 排序，输出 `top_k` 条并连续编号。

## 二、配置项怎么选

| 配置 | 含义 | 容易误解的点 |
| --- | --- | --- |
| 自动 / 手动路由 | 自动走"规则 + 模型理解"；手动只用规则理解，省一次模型调用 | 手动**不是**"执行全部策略" |
| 策略允许列表 | "可以用哪些策略" | 勾上 ≠ 一定执行；规则没命中、依赖缺失、预算不够都不会执行 |
| 策略预算 | 本次最多执行几个策略，按优先级从高到低 | 预算小于命中数时，后面的策略记为"被预算拦截" |
| 质量阈值 | 判定"召回充分"的相似度门槛（0–1） | 它不参与检索过滤，只参与结论判定 |
| top_k | 每路检索取多少片段 | 两路都取这么多，融合后再截到 top_k |

HyDE 与 Step-back 在注册表里以 `enabled=False` 存在：决策表会显示"未启用"，不会产生改写文本，也不会增加检索。

## 三、怎么看结果

- **决策表**：固定 7 行（与注册表一致）。关注"执行"之外的四种状态：未触发（规则没命中）、被允许列表拦截、被预算拦截、未启用。理由列会说明具体原因。
- **改写前后**：主查询按执行顺序串联，所以后一条的"改写前"是前一条的"改写后"。
- **双路指标**：最高分、达到阈值的片段数、覆盖文档数、命中片段数。改写组未执行时显示"未完成"，不用 0 冒充。
- **增益 `lift`** = 改写组 `top1` − 对照组 `top1`，保留四位小数：
  - `+0.0400`：改写把最相关片段的相似度抬高了 0.04；
  - 负数：改写把召回改差了，通常意味着改写引入了原文没有的概念或丢掉了限定词；
  - 接近 0：两者打平，优先选成本更低的配置。
- **噪声底约 0.001**：同一条查询分两次调用 embedding 检索，`top1` 会在第四位小数上抖动（实测 0.310436 vs 0.309839）。因此 `|lift| < 0.005` 应当视为"没有差别"，不要解读成微弱提升或下降。
- **`lift` 只是最高分差**，不代表整体召回更好。同时看"达到阈值片段数"和"覆盖文档数"：最高分涨了但达标片段变少，往往是改写过度收窄。
- **顶部提示**：超时、预算截断、策略降级、低置信度都会单独提示；预算截断会列出被拦的策略名。
- **成本**：模型调用数、检索查询数、嵌入批次、总耗时。改写组查询越多，检索与嵌入成本越高。

## 四、接口

```http
POST /api/v1/retrieval/rewrite-lab/run
Authorization: Bearer <token>
Content-Type: application/json

{
  "query": "它和《员工手册》里的年假规定有什么区别？同时调休怎么算？",
  "history": [{"role": "user", "content": "年假怎么算"}],
  "mode": "auto",
  "allowlist": ["context", "entity", "semantic", "decompose", "multi"],
  "budget": 5,
  "quality_threshold": 0.6,
  "top_k": 5
}
```

返回 `RewriteTrace`，包含 `request / understanding / routing / workflow / rewrites / arms / evaluation / second_stage / fusion / totals / degraded / warnings`。
Trace 只带改写文本、证据与指标，**不包含提示词全文**；`llm_calls`、`retrieval_calls`、`embed_calls` 与实际调用一一对应，可逐条对账。

## 五、复现一次对照实验

1. 确认后端已配置 embedding 与 LLM（未配置时接口返回 503，页面提示检查配置）。
2. 库里要有已发布、已有片段的文档；空库跑出来的分数没有意义。
3. 用同一批问题（建议 ≥5 条，覆盖指代、口语、复合问题、别名、直问）依次跑三组：
   - 关闭改写：Allowlist 全部取消，预算 1；
   - 只开语义改写：Allowlist 只留"语义改写"，预算 2；
   - 全开：五个策略，预算 5。
4. 记录每条问题的 `lift`、`baseline.top1`、`rewritten.top1`、`above_tau`、`docs`、`elapsed_ms` 与 `warnings`。
5. 判定标准：
   - 全开组平均 `lift` 明显为正，且达标片段数与覆盖文档数没有下降 → 可以考虑在问答链路默认开启；
   - 只开语义组与全开组差距很小 → 默认只开语义改写，省模型调用；
   - 出现负增益的问题集中在某一策略 → 先收紧该策略的触发条件，而不是调阈值。

自动化脚本：`python -m backend.scripts.query_rewrite_benchmark`（在项目根目录，或 `cd backend` 后 `python -m scripts.query_rewrite_benchmark`）。
脚本会临时插入一小批测试语料、跑三组对照、输出 Markdown 表与原始 Trace JSON，结束后清理语料。
使用真实模型会产生调用费用，按需运行。

## 六、常见问题

- **运行按钮点不动**：查询为空或上一次运行还没结束。
- **决策表里"执行"但改写前后一样**：实体标准化把别名替换成了同名标准名，属于正常结果。
- **改写组显示"未完成"**：超时或预算在改写阶段耗尽，本次只有对照组有效；这不是 0 分，也不代表改写无效。
- **`warnings` 里提示低置信度**：结论不足 `sufficient`，请结合 `above_tau` 判断是语料问题还是改写问题。
